What is Microsoft Sentinel Data Lake?

Microsoft Sentinel Data Lake is a purpose-built, cloud-native security data lake that transforms how organizations manage and analyze security data at scale. Released for general availability on September 30, 2025, it represents a fundamental evolution of the traditional SIEM model by decoupling storage from compute.

Key Definition

A security data lake centralizes diverse security data sources into a single, open-format repository using delta parquet files. Unlike traditional SIEMs that couple storage and compute, data lakes enable flexible querying across multiple analytics engines while maintaining cost-effective long-term retention.

The Data Volume Challenge

Enterprise organizations face exponential growth in security telemetry. A typical enterprise generates 25+ TB/day of security logs across endpoints, identity systems, cloud platforms, and network infrastructure.

Traditional SIEM economics force painful tradeoffs:

  • Reduce logging → Security blind spots
  • Shorten retention → Compromised forensic depth
  • Full coverage → Unsustainable costs

The Data Lake Solution

Sentinel Data Lake breaks this paradox by separating storage economics from analytics performance:

  • Tiered Storage: Hot analytics tier + cold data lake tier
  • Single Copy: Data mirrored automatically, no duplication costs
  • Open Format: Delta parquet enables multi-engine analytics
  • 12-Year Retention: Meet compliance requirements affordably

Data Lake Architecture

Understanding the technical architecture is crucial for designing effective implementation strategies and optimizing security operations workflows.

Two-Tier Storage Model

Analytics Tier (Hot)

High-Performance Security Operations

Capabilities

  • Real-time alerting and detection rules
  • Interactive KQL queries
  • Advanced hunting
  • Workbooks and dashboards
  • Incident management
  • UEBA behavioral analytics

Specifications

  • Default: 30 days retention
  • Free: Up to 90 days
  • Maximum: 2 years
  • Performance: Sub-second queries
  • Use Case: Active SOC workflows
Data Lake Tier (Cold)

Cost-Effective Long-Term Storage

Capabilities

  • Historical investigations (365+ days)
  • Forensic analysis
  • Threat intelligence retrospective matching
  • Compliance/regulatory retention
  • ML model training
  • Baseline and trend analysis

Specifications

  • Retention: 30 days to 12 years
  • Compression: 6:1 ratio
  • Format: Delta Parquet (open)
  • Latency: 90-120 min from ingest
  • Query: KQL jobs, Notebooks
⚠️ Critical Architecture Decision

Do not move tables from Analytics tier to Data Lake tier. Moving a table from Analytics to Data Lake tier stops all real-time features (alerting, analytics rules, detection). Instead, configure both Analytics retention (e.g., 90 days) AND Total retention (e.g., 365 days) to keep tables in Analytics while extending storage to the lake.

Table Configuration Model

Understanding table settings is essential for proper implementation. Each table can be configured independently for tier and retention.

Analytics + Lake (Recommended)

Tables remain in Analytics tier with automatic mirroring to Data Lake for extended retention.

// Recommended configuration Table: SecurityEvent Tier: Analytics Analytics Retention: 90 days Total Retention: 365 days // Result: // - Days 0-90: Analytics tier (hot) // - Days 91-365: Data Lake tier (cold) // - Detections continue working ✓

Lake-Only (Secondary Data)

High-volume, low-fidelity logs stored directly in Data Lake without analytics tier ingestion.

// Cost-optimized for verbose logs Table: ProxyLogs_CL Tier: Data Lake Retention: 365 days // Result: // - No real-time detection ✗ // - Forensic access via KQL jobs ✓ // - Lowest storage cost ✓

Technical Specifications

Storage Architecture

▼
  • Format: Delta Parquet (columnar, open-source)
  • Compression: 6:1 uniform ratio across all data sources
  • Region: Data lake provisioned in same region as primary Sentinel workspace
  • Encryption: Microsoft-managed keys (CMK not supported for data lake tier)
  • Data Availability: 90-120 minutes after ingestion for lake tier

Service Limits

▼
  • Analytics Retention: 30 days to 2 years
  • Total Retention: 30 days to 12 years
  • KQL Job Timeout: 1 hour maximum per job
  • Concurrent Jobs: Per-tenant limits apply
  • Data Promotion Latency: 15-30 minutes to appear in Advanced Hunting

Prerequisites

▼
  • Microsoft Sentinel workspace connected to Microsoft Defender portal
  • Azure subscription and resource group for billing
  • Direct subscription owner (management-group level insufficient)
  • Unified RBAC permissions: 'Data (manage)' in Data operations group
  • Azure RBAC: Log Analytics Contributor for table management

Implementation Strategy

Enterprise implementation requires careful planning across multiple workstreams. This section covers a phased approach suitable for large-scale deployments (25+ TB/day).

Phased Implementation Timeline

Phase 1: Discovery (Weeks 1-2)

Baseline and Assessment

Establish current-state metrics and identify dependencies before any changes.

Key Activities

  • Baseline daily ingestion by table (GB/day) and identify top volume drivers
  • Capture SOC query patterns: lookback distribution (7/30/90/365 days)
  • Quantify restore/search usage frequency and time impact
  • Inventory all analytics rules, hunting queries, workbooks, and ASIM dependencies
  • Document SecurityEvent dependencies for tables requiring >90 day lookbacks

Exit Criteria

  • ≥95% of ingestion attributed to known tables/sources
  • Top 20 hunts mapped to lookback requirements
  • Baseline report approved by stakeholders
Phase 2: Design (Weeks 3-4)

Target State Architecture

Define tiering strategy, SOC workflows, and governance controls.

Key Decisions

  • Table Configuration: Keep all tables in Analytics tier; set Analytics retention 90 days, Total retention 365 days
  • SOC Decision Tree: ≤90 days = analytics-first; >90 days = lake-first + KQL jobs
  • SecurityEvent Bridge: Enable Archive before data lake for legacy data access
  • RBAC Model: Unified RBAC in Defender portal + Azure RBAC for workspace
  • FinOps Guardrails: Budgets, query templates, approval workflows for broad scans
Phase 3: Pilot (Weeks 5-7)

Controlled Validation

Enable data lake with limited analyst cohort to validate workflows.

Validation Points

  • Onboard data lake in Defender portal; verify provisioning
  • Configure retention on pilot tables: Analytics 90d, Total 365d
  • Validate tables remain in Analytics tier (detection rules continue)
  • Run golden investigations across 7/30/90/365 day windows
  • Test KQL jobs for batch processing; validate service limits
  • Confirm cost guardrails trigger appropriately

Success Metrics

  • ≥95% pilot investigations completed without restore/search (post-enable data)
  • No critical detection regressions
  • Lake workflows meet agreed SLOs
Phase 4: Scale Rollout (Weeks 8-11)

Organization-Wide Enablement

Extend tier-aware workflows to full SOC with training and dashboards.

Rollout Activities

  • Train SOC and IR teams: tier decision tree, lake patterns, KQL jobs
  • Update SOC knowledge base: replace restore-first with lake-first guidance
  • Deploy operational dashboards: freshness, availability, job status, costs
  • Enable governance cadence: weekly hotspot review, retention compliance
  • Run weekly regression tests against baseline

Success Metrics

  • Restore/search usage reduced ≥50% for post-enable lookbacks
  • ≥80% SOC adoption of tier-aware workflows
Phase 5: Cutover (Week 12)

Production Default

Tier-aware workflows become the standard operating model.

Cutover Checklist

  • Formal cutover announcement with effective date
  • Update default workbook time pickers to 90 days
  • Publish standard 365-day lake workflow documentation
  • Validate all table settings: Analytics tier, 90d analytics, 365d total
  • Execute stop-the-line checks: ingestion, detections, budgets, jobs
Phase 6: Optimization (Ongoing)

Continuous Improvement

Regular review and refinement of patterns, costs, and governance.

Governance Cadence

  • Monthly: Lake query hotspot review, job optimization, access audit
  • Quarterly: Content refresh, performance tuning, risk register update
  • Annual: Architecture review, retention policy assessment

Historical Data Considerations

🔴 Critical Constraint

Historical data in Log Analytics Archive is not automatically migrated to Sentinel Data Lake. Plan for coexistence during the transition period.

Option 1: Coexistence Bridge

Recommended

  • Keep existing Archive for pre-enable periods
  • Use Data Lake for post-enable investigations
  • After 12 months, lake contains full 365 days

Effort: Low | Risk: Low

Option 2: Restore-on-Demand

Acceptable

  • Keep Archive as-is indefinitely
  • Continue restore/search for all historical
  • Highest analyst friction

Effort: Lowest | Risk: Medium

Option 3: Export/Backfill

Complex

  • Export historical to ADX or external store
  • High cost at 25+ TB/day scale
  • Only for regulatory requirements

Effort: High | Risk: High

Advanced Hunting

Advanced Hunting is the unified query experience in the Defender portal, allowing KQL queries across both XDR tables and Sentinel data. With Data Lake enabled, queries can span up to 12 years of historical data.

Query Scope

XDR Data (Native)

  • Device* tables (Endpoint)
  • Identity* tables (Identity)
  • Email* tables (Office 365)
  • CloudApp* tables (Cloud Apps)
  • Alert and incident tables

30 days default retention, extendable via Data Lake

Sentinel Data (Connected)

  • All Sentinel tables
  • Custom log tables (*_CL)
  • Third-party connectors
  • Azure service logs
  • Data Lake tier tables

Retention based on table configuration

Cross-Domain Query Examples

// Correlate endpoint malware with email delivery // Find if malware on device came from email attachment let MalwareDevices = DeviceEvents | where TimeGenerated > ago(7d) | where ActionType == "AntivirusDetection" | project DeviceName, SHA256, DetectionTime = TimeGenerated; EmailAttachmentInfo | where TimeGenerated > ago(7d) | join kind=inner MalwareDevices on SHA256 | project RecipientEmailAddress, SenderFromAddress, FileName, Subject, DetectionTime, DeviceName
// Track lateral movement from identity to endpoint // User authenticated, then appeared on new device IdentityLogonEvents | where TimeGenerated > ago(24h) | where LogonType == "Interactive" | summarize FirstSeen = min(TimeGenerated), DevicesSeen = make_set(DeviceName) by AccountUpn | where array_length(DevicesSeen) > 3 | project AccountUpn, DevicesSeen, FirstSeen
// Hunt for data exfiltration: large file uploads to cloud apps CloudAppEvents | where TimeGenerated > ago(7d) | where ActionType == "FileUploaded" | summarize TotalUploadMB = sum(ActivityObjects[0].Size) / 1048576, FileCount = count() by AccountDisplayName, Application | where TotalUploadMB > 100 | order by TotalUploadMB desc

Data Lake Long-Range Queries

With Data Lake enabled, use the time picker or KQL time filters to query historical data beyond the analytics tier:

// Historical threat hunt: Search for IOC across 365 days // This query runs against the Data Lake tier let SuspiciousHash = "a1b2c3d4e5f6..."; DeviceFileEvents | where TimeGenerated > ago(365d) // Data Lake query | where SHA256 == SuspiciousHash | project TimeGenerated, DeviceName, FileName, FolderPath, InitiatingProcessFileName, InitiatingProcessAccountName
⚠️ Query Performance

Analytics Tier: Sub-second to seconds for most queries.
Data Lake Tier: May take 90-120+ seconds. For queries >2 minutes, use KQL Jobs or async mode. Always filter by time first, then entity.

Automated Investigation & Response

Automated Investigation and Response (AIR) in Defender XDR automatically investigates alerts and takes remediation actions, reducing analyst workload and response time.

AIR Workflow

1

Alert Triggers Investigation

An alert matching AIR criteria automatically starts an investigation. This includes malware alerts, suspicious behavior, and certain identity alerts.

2

Evidence Collection

AIR collects related evidence: processes, files, registry keys, network connections, and user activities connected to the alert.

3

Verdict Determination

Each piece of evidence is analyzed and assigned a verdict: Malicious, Suspicious, Clean, or Unknown.

4

Remediation Actions

Based on verdicts, AIR proposes or takes remediation actions (depending on automation level): quarantine file, stop process, disable user, etc.

Automation Levels

Level Behavior Use Case
No automation No automated actions; all manual High-compliance environments
Semi Approval required for all actions Balanced control and speed
Semi (exclude folders) Auto-approve except for sensitive paths Protect critical file locations

KQL & Analytics

Mastering Kusto Query Language (KQL) for data lake exploration is essential for security analysts performing historical investigations and forensic analysis.

Data Lake Exploration

After onboarding, access KQL queries under Microsoft Sentinel → Data lake exploration in the Defender portal. The query editor supports IntelliSense, autocomplete, and query history.

Interactive Queries

Run ad-hoc KQL queries directly on data lake resources for immediate results. Best for:

  • Forensic analysis of specific incidents
  • Entity-focused investigations
  • Quick lookups with time bounds

Limit: 2-minute timeout; async option for longer queries

KQL Jobs

One-time or scheduled asynchronous queries for batch processing. Best for:

  • Long-running incident investigations
  • Historical TI matching scans
  • Anomaly detection across tables
  • Data promotion to analytics tier

Limit: 1-hour timeout per job

Query Best Practices

✅ Performance Optimization

Data lake queries scan potentially massive datasets. Always apply these patterns to minimize scan volume and cost:

kql_best_practices.kql 
// ❌ BAD: Broad scan with no time filter
SecurityEvent
| where AccountType == "User"

// ✅ GOOD: Time-first filtering (always)
SecurityEvent
| where TimeGenerated > ago(30d)
| where AccountType == "User"

// ✅ BETTER: Entity-first + time bounds
SecurityEvent
| where TimeGenerated between (datetime(2025-06-01) .. datetime(2025-06-30))
| where Account == "CONTOSO\\jsmith"
| project TimeGenerated, Activity, Computer, IpAddress

// ✅ BEST: Staged query for large investigations
let targetEntities = dynamic(["jsmith", "malware.exe"]);
let timeWindow = 7d;
SecurityEvent
| where TimeGenerated > ago(timeWindow)
| where Account has_any (targetEntities) or Process has_any (targetEntities)
| summarize count() by bin(TimeGenerated, 1h), Activity
| order by TimeGenerated desc

KQL Job Use Cases

1

Data Promotion

Promote specific historical data from lake tier to analytics tier for advanced hunting. Results appear in 15-30 minutes.

2

Scheduled TI Matching

Retrospective threat intelligence scans against months of historical data to detect previously unknown indicators.

3

Baseline Building

Aggregate historical patterns for anomaly detection models. Schedule recurring jobs to update baselines.

4

Forensic Investigation

Deep-dive analysis across extended timeframes for incident response. Use joins and unions across multiple tables.

Creating a KQL Job

job_example.kql 
// Promote suspicious sign-in data for detailed analysis
// Job Name: HighRisk_Signins_Investigation_2025Q4
// Schedule: One-time
// Destination: InvestigationResults_KQL_CL (new table)

SigninLogs
| where TimeGenerated between (datetime(2025-10-01) .. datetime(2025-12-31))
| where RiskLevelDuringSignIn in ("high", "medium")
| where ResultType != "0"  // Failed sign-ins only
| summarize 
    FailedAttempts = count(),
    UniqueIPs = dcount(IPAddress),
    RiskSignals = make_set(RiskEventTypes)
    by UserPrincipalName, AppDisplayName, Location
| where FailedAttempts > 10
| project 
    UserPrincipalName,
    AppDisplayName,
    Location,
    FailedAttempts,
    UniqueIPs,
    RiskSignals

// InvestigationResults_KQL_CL | take 100
